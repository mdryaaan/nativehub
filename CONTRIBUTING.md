# Contributing to NativeHub

Thanks for wanting to help. Corrections are the single most valuable contribution here — this site
is only useful if it is right, and being wrong in public is only useful if it gets fixed.

## Development environment

**Requirements:** Node.js 20 or newer (22 is what CI uses) and npm 10+.

```bash
git clone https://github.com/mdryaaan/nativehub.git
cd nativehub
npm install
npm run start
```

The dev server runs at <http://localhost:3000/nativehub/> with hot reload. Note the `/nativehub/`
path — it is the configured `baseUrl`, and omitting it gives you a 404.

| Command                | What it does                                                |
| ---------------------- | ----------------------------------------------------------- |
| `npm run start`        | Dev server with hot reload                                  |
| `npm run build`        | Production build. Fails on broken links and broken anchors. |
| `npm run serve`        | Serve the production build locally                          |
| `npm run typecheck`    | `tsc --noEmit`                                              |
| `npm run lint`         | ESLint over `src/`, zero warnings tolerated                 |
| `npm run lint:fix`     | ESLint with autofix                                         |
| `npm run format`       | Prettier, write mode                                        |
| `npm run format:check` | Prettier, check mode — this is what CI runs                 |
| `npm run clear`        | Clear the Docusaurus cache when something looks stale       |

Run `npm run build && npm run lint && npm run format:check && npm run typecheck` before opening a
PR. That is exactly what CI runs.

## Project layout

```
nativehub/
├── .github/workflows/     ci.yml, links.yml
├── docs/
│   ├── learn/             concept pages  → /docs/learn/*
│   └── guides/            task pages     → /docs/guides/*
├── blog/                  posts, authors.yml, tags.yml
├── src/
│   ├── components/        reusable React components
│   ├── pages/             standalone routes (/, /tools, /resources, /about)
│   ├── css/               custom.css (design system) + tailwind.css
│   └── theme/             swizzled Docusaurus components (Footer, NotFound)
├── static/                copied verbatim into the build output
├── docusaurus.config.ts   site config + the latest-posts plugin
├── sidebars.ts            the Learn and Guides sidebars
└── tailwind.config.js
```

Which one do you want?

- **`docs/learn/`** — explains a concept. Reference-shaped, read in any order.
- **`docs/guides/`** — accomplishes a task. Numbered steps, start to finish.
- **`blog/`** — an article with a date and an opinion. Not a reference.
- **`src/pages/`** — a bespoke page that is not primarily prose.

## Adding a doc page

1. Create the file under `docs/learn/` or `docs/guides/` with an `.mdx` extension and a
   kebab-case name.

2. Add front matter:

   ```yaml
   ---
   id: kubernetes-jobs
   title: Kubernetes Jobs and CronJobs
   sidebar_label: Jobs & CronJobs
   sidebar_position: 7
   description: One-sentence summary — this becomes the meta description and search snippet.
   keywords: [kubernetes, jobs, cronjobs, batch]
   ---
   ```

3. Register it in `sidebars.ts`. Sidebars are explicit rather than autogenerated, so the file will
   not appear until you add its id:

   ```ts
   items: [
     'learn/docker-fundamentals',
     // …
     'learn/kubernetes-jobs',
   ],
   ```

4. Import any components you need at the top of the file, after the front matter:

   ```mdx
   import CalloutBox from '@site/src/components/CalloutBox';
   import CodeTabs from '@site/src/components/CodeTabs';
   ```

5. Link to sibling pages with a relative path **including the extension**, so the build can verify
   it: `[Helm basics](./helm-basics.mdx)`. Cross-section links use `../guides/deploy-first-app.mdx`.
   Links to non-docs routes use the site path: `/tools`, `/blog/what-is-oci-bundle`.

`showLastUpdateTime` is enabled, so the "Last updated" stamp comes from the file's last commit —
there is nothing to maintain by hand.

## Adding a blog post

1. Create `blog/YYYY-MM-short-slug.mdx`.

2. Front matter — `slug` controls the URL, and `date` controls ordering:

   ```yaml
   ---
   slug: kubernetes-jobs-in-practice
   title: Kubernetes Jobs in practice
   authors: [mdryaaan]
   tags: [kubernetes, fundamentals]
   date: 2026-08-01
   description: One or two sentences. Used for the meta description and the homepage card.
   image: /img/social-card.png
   ---
   ```

3. Add a truncation marker after the intro. The build **fails** without one
   (`onUntruncatedBlogPosts: 'throw'`), because an untruncated post floods the list page:

   ```mdx
   {/* truncate */}
   ```

4. Authors must exist in `blog/authors.yml` and tags in `blog/tags.yml`. Both are configured to
   throw on unknown values rather than silently inventing them. To add a tag:

   ```yaml
   observability:
     label: Observability
     permalink: /observability
     description: Metrics, logs, and traces.
   ```

Reading time is computed automatically. The homepage's "Latest from the blog" section is generated
by the `nativehub-latest-posts` plugin in `docusaurus.config.ts`, so a new post appears there with
no extra work.

## Adding a reusable component

Components live one per directory under `src/components/`:

```
src/components/MyComponent/
├── index.tsx        default export, props interface exported too
└── styles.css       plain CSS, or styles.module.css for scoped styles
```

Conventions:

- **Type the props** and export the interface, so MDX authors get autocomplete.
- **Read design tokens, never hard-code colour.** Use `var(--nh-*)` and `var(--ifm-*)` so the
  component works in both themes automatically. See the token list at the top of
  `src/css/custom.css`.
- **Plain `.css` when MDX needs the class names** (as in `CalloutBox`), **`.module.css` otherwise**.
  Remember that inside a module, a global class such as Infima's `.button` must be written
  `:global(.button)`.
- **Tailwind is additive.** Preflight and `container` are disabled in `tailwind.config.js` so
  Infima keeps ownership of base element styles.
- **Decorative SVGs get `aria-hidden="true"`**; interactive elements get an accessible name.
- **Respect `prefers-reduced-motion`** — the global rule in `custom.css` covers transitions and
  animations, but not JavaScript-driven motion.

Then use it from MDX:

```mdx
import MyComponent from '@site/src/components/MyComponent';

<MyComponent prop="value" />
```

## Writing style

The bar for content here is _technically correct, or not published_.

- **Verify against the primary source.** The Kubernetes docs, the OCI specs, or the code. Not
  another blog post.
- **Every command must run as written.** If you cannot run it, do not include it.
- **Explain the mechanism, not just the recipe.** "A ClusterIP is a virtual address realised as
  iptables NAT rules" beats "a Service load balances traffic."
- **Show the failure mode.** The part readers actually need is what breaks and why.
- **Say when something is uncertain**, rather than smoothing over it.
- **No marketing voice.** No "simply", "just", or "easy" — if it were easy the page would not exist.
- **British or American spelling are both fine**; be consistent within a page.

## Branches and commits

Branch from `main`:

```
<type>/<short-description>
```

| Prefix      | For                                           |
| ----------- | --------------------------------------------- |
| `feat/`     | New page, post, component, or feature         |
| `fix/`      | Corrections to content, styling, or behaviour |
| `docs/`     | README, CONTRIBUTING, and other repo docs     |
| `chore/`    | Dependencies, config, tooling                 |
| `refactor/` | Restructuring with no behaviour change        |

Examples: `feat/kubernetes-jobs-guide`, `fix/networking-dns-typo`.

Commits follow [Conventional Commits](https://www.conventionalcommits.org/), lowercase, imperative,
with an optional scope:

```
feat(docs): add kubernetes jobs guide
fix(theme): correct code block contrast in dark mode
docs: expand contributing guide
chore(deps): bump docusaurus to 3.10.2
```

Keep the subject under about 72 characters. Small, focused commits are easier to review and easier
to revert.

## Pull request checklist

Before requesting review:

- [ ] `npm run build` passes — this also catches broken internal links and anchors.
- [ ] `npm run lint` passes with zero warnings.
- [ ] `npm run format:check` passes (`npm run format` fixes it).
- [ ] `npm run typecheck` passes.
- [ ] New pages are registered in `sidebars.ts` and reachable from navigation.
- [ ] New blog posts have `{/* truncate */}`, a known author, and known tags.
- [ ] Every command in the page has actually been run.
- [ ] Checked in **both** light and dark themes.
- [ ] Checked at mobile width (≤480px) as well as desktop.
- [ ] Images have meaningful `alt` text; decorative graphics are `aria-hidden`.
- [ ] Headings step down one level at a time, with exactly one `h1` per page.
- [ ] Links to external sites point at the primary source.

In the PR description, say what changed and why. If it is a correction, link the source that shows
the previous version was wrong — that makes review fast and keeps the standard honest.

## Code of conduct

Be decent. Assume good faith, critique the content rather than the person, and remember that
someone filing a correction is doing you a favour.
